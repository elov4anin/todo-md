# TASK-todo-md-release-epic-layout: Подготовить релиз поддержки каталогов эпиков

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- После реализации каталогов `EPIC-*` и адаптации dashboard изменится пользовательское поведение CLI, но текущая версия пакета останется `1.0.0`, если не выполнить отдельную релизную работу.
- Версия одновременно хранится в `package.json` и `package-lock.json`; ручное неполное изменение оставит пакет в несогласованном состоянии.
- Без новой секции `CHANGELOG.md` потребители не узнают о канонических путях, совместимости со старыми плоскими файлами, поведении переходов, файловых ссылках dashboard и возможных действиях при обновлении.

### Варианты или путь решения (Solution Sketch)
- После завершения обеих зависимых задач оценить фактическую совместимость публичного CLI по SemVer и выбрать следующий номер версии.
- Синхронно обновить npm metadata без автоматического Git-тега, затем добавить верхнюю датированную секцию changelog с пользовательскими изменениями и миграционными примечаниями.
- Перед передачей релиза выполнить полный check и проверить состав npm-пакета.

### Ожидаемый результат (Expected Result)
- Пакет имеет единый новый номер версии во всех npm-файлах.
- `CHANGELOG.md` позволяет пользователю понять, что изменилось, какие пути теперь создаёт CLI и требуется ли адаптировать скрипты, работающие с именами файлов.
- Релизная метаинформация соответствует фактически реализованному и проверенному поведению двух зависимых задач.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> **User Story:** Как потребитель `todo-md`, я хочу получить версионированное и документированное обновление поддержки каталогов эпиков, чтобы безопасно обновить Git dependency и при необходимости адаптировать автоматизацию к новым путям.

### Цель по SMART (Goal)
- После завершения `TASK-todo-md-epic-directory-layout` и `TASK-todo-md-dashboard-epic-paths` повысить версию выше `1.0.0`, синхронизировать npm metadata, добавить датированную секцию `CHANGELOG.md` и подтвердить релиз командами `npm run check` и `npm pack --dry-run`.

## 2. Контекст и Границы (Context and Scope)

- **Где делаем:** `package.json`, `package-lock.json`, `CHANGELOG.md`; документацию затрагивать только для устранения найденного при релизной проверке противоречия.
- **Текущая версия:** `1.0.0` в `package.json`, `package-lock.json.version` и `package-lock.json.packages[""].version`.
- **Формат changelog:** новая версия добавляется сразу после `# Changelog`; заголовок `## [X.Y.Z] — YYYY-MM-DD`, далее только применимые секции `Added`, `Changed`, `Fixed`, `Security`, `Removed`.
- **SemVer-решение:** оценить итоговый diff, документацию и публичное поведение. Изменение путей, возвращаемых `create` и переходами, нужно явно классифицировать; исправление по документированному контракту не объявлять автоматически patch без анализа влияния на скрипты потребителей.
- **Согласованность сборки:** обе зависимые задачи должны уже включать скомпилированный `dist/`; release-задача не должна маскировать рассинхронизацию исходников и сборки.
- **Границы (Out of Scope):** публикация в npm, создание Git-тега/GitHub Release, push, merge, изменение версии Node.js, добавление release automation и включение новых функциональных изменений в релизный коммит.

- [ ] Обновить версию одной командой `npm version <version> --no-git-tag-version`, чтобы синхронизировать `package.json` и `package-lock.json` без коммита и тега.
- [ ] Проверить равенство `package.json.version`, `package-lock.json.version` и `package-lock.json.packages[""].version`.
- [ ] Добавить в начало `CHANGELOG.md` секцию новой версии с фактической датой релизной подготовки.

- [ ] Описать обратную совместимость со старыми плоскими файлами и нормализацию затронутого файла изменяющей командой либо фактическую альтернативу, реализованную в зависимой задаче.
- [ ] Описать изменения dashboard: вложенные файлы, автоматическая база directory-mode, правила `--base` для JSONL и защита файловых ссылок — только если эти пункты реально реализованы.

- [ ] Не включать в changelog незавершённые optional/should требования и не выдавать тестовое покрытие или security-fix за выполненные без проверки diff.
- [ ] Выполнить `npm run check`, включая typecheck, tests, compile, verify-dist и валидацию всей доски.
- [ ] Выполнить `npm pack --dry-run` и убедиться, что новый номер версии и необходимые `dist`, `assets`, docs, schemas входят в пакет, а lifecycle-скрипты не появились.

### 🟡 Желательно (Should Have)
- [ ] Сгруппировать changelog по пользовательскому эффекту, а не по именам внутренних функций и файлов.
- [ ] Упомянуть количество добавленных регрессионных тестов только после подсчёта фактического diff.

### 🟢 Опционально (Could Have)
- [ ] Добавить ссылку на release/tag в заголовок changelog, если проект начнёт использовать ссылочные определения версий единообразно.

### ⚫ Won't Have (Не будем делать)
- Не запускать `npm publish` и не снимать `private: true`.
- Не создавать Git-тег, commit, push или GitHub Release без отдельного явного запроса.
- Не менять функциональный код под видом релизной подготовки.
- Не переписывать историю старых секций `CHANGELOG.md` без обнаруженной фактической ошибки.
- Не выбирать номер версии только по названиям `fix`/`chore` задач без оценки публичного поведения CLI.

## 7. Риски и зависимости (Risks and Dependencies)
- **Зависимости:** `TASK-todo-md-epic-directory-layout`, затем `TASK-todo-md-dashboard-epic-paths`; релиз описывает только их завершённый результат.
- **Риск неверного SemVer:** новая файловая раскладка может ломать внешние shell-скрипты, даже если CLI читает legacy-layout; решение требует явного анализа публичного контракта.
- **Риск рассинхронизации:** прямое редактирование только `package.json` оставит старую версию в lockfile; использовать npm-команду без Git-тега.
- **Риск неточного changelog:** постановки задач содержат желательные и опциональные пункты; release notes строятся по реализации, а не по плану.
- **Ограничение окружения:** `npm pack --dry-run` не должен обращаться к сети, но может использовать npm-cache; при проблеме cache указать временный cache в `/tmp`.
